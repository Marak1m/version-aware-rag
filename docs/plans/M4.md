# M4 plan: corpus and retrieval (draft for review)

Status: draft, 2026-10-08. Nothing below is built yet.

## Goal and acceptance

M4 builds the version-tagged documentation corpus and the v0 retrieval step that every method
will share (handoff, "Documentation corpus and retrieval"). Acceptance, from the handoff with the
user's change to example checking:

1. Gold chunks exist for both versions of every concept, and for both versions of each control's
   shared symbol. `bench validate` step 7 runs (`check_gold_chunks`) and passes for all four.
2. Every chunk carries complete provenance.
3. Every example kept in the corpus ran without error in its tagged environment. Failing and
   timed-out examples are dropped and logged; deprecation warnings are recorded on the chunk;
   `discriminative: true` marks an example that fails in the other environment.
4. The doc-conflict test is true for pd-001, np-001 and pyd-001, and false for ctl-np-001.

## Decisions for review (each has the default I will build with)

| # | Question | Default |
| --- | --- | --- |
| D1 | How are chunk tokens counted for the 350-token cap? | The Qwen2.5-Coder tokenizer: `tokenizer.json` downloaded once at a pinned Hugging Face revision, stored with its sha256, read with the `tokenizers` package (new orchestrator dependency). Fallback if the download fails: a regex word-piece estimate, flagged in provenance. |
| D2 | The handoff says chunks are 200 to 350 tokens. A five-part chunk for a small function is often under 200. | Enforce the 350 cap only, by trimming example lines and then the description. Report the length distribution; do not pad. |
| D3 | Distractors come from "the rest of the corpus". If a BM25 distractor is version-exclusive, the control's conflict test turns true by luck. | Draw distractors only from chunks whose symbols are `shared_same` or `shared_unknown`. The conflict is then decided by the gold chunks alone, as the handoff intends ("the conflict never depends on retrieval luck"). |
| D4 | Migration chunks need the release notes "fetched at a pinned tag". They are off by default and must be distilled rules when on. | Build migration chunks as one-line rules from `data/rules/` (replacements, expired attributes, Field keywords), each citing its rule source. Fetching raw release notes is deferred until the `include_migration` ablation runs. |
| D5 | Gold symbols can be keywords (`pydantic.Field(regex)`, `pandas.read_csv(date_parser)`). Which chunk is gold? | The owner's chunk (`pydantic.Field`), and step 7 also checks that the owner's signature in that version contains the keyword. |
| D6 | The doc-conflict test lists `old_only`, `new_only` and `shared_changed`. Should `deprecated_in_new` also make a set conflicting? | No, keep the handoff's three buckets. A deprecated-but-working API does not make the answer version-dependent. |
| D7 | Examples are library-authored code run outside the WSL2/container rule, which covers model output. Some read URLs. | Run them on this host in a temp cwd with the stripped environment and the timeout. Examples that contain `http://` or `https://` are dropped unrun and logged as `network`. |
| D8 | Commit the corpus? | Yes: `data/corpus/{library}/{version}.jsonl` plus an example-check cache, a few MB per library, so every run can cite exact chunks. |

## Corpus scope

- One API chunk per symbol of kind function, method, class or attribute in each version's
  inventory. Parameters live inside their owner's signature; modules and config keys get no chunk
  of their own (pydantic config keys are covered by the config docs sections).
- pandas and NumPy: the installed docstring, read inside the verified environment by a new
  stdlib-only script, so the version tag is true by construction.
- pydantic: sections of the docs markdown at the release tag, split by heading.
  - 1.10.13: `docs/usage/*.md`, whose examples are include directives
    (`{!.tmp_examples/schema_main.md!}`) resolved to `docs/examples/*.py` at the same commit.
  - 2.13.4: `docs/concepts/*.md`, `docs/migration.md` excluded (it is migration material, D4),
    with inline `python` fences. The `docs/api/*.md` pages are mkdocstrings stubs and are skipped.
  - Each file is fetched at the tag's commit SHA; tag, SHA, path and file sha256 go into
    provenance (verification check 6).
  - Sections map to symbols by backticked names (`Field`, `model_dump`, `` `regex` ``); the seed
    concepts' gold symbols are mapped by hand in `data/corpus/pydantic/seed_map.yaml`.
  - A pydantic symbol with no docs section falls back to its docstring, marked `source.type: docstring`.

## Chunk composition

Five parts in this order (handoff L11):

1. Fully qualified name.
2. Version tag.
3. The exact signature for that version, from the inventory, not the docstring.
4. A one-line description: the docstring summary, or the section's first sentence.
5. One short example.

A deprecation note from the docstring (a `.. deprecated::` directive or the
summary-region text) is kept as one line after the description. `strip_deprecation_notes`
removes it. The rendered header is `[{library} {version} | {kind}] {title}`, controlled by
`show_version_tags`.

Example extraction from a numpydoc `Examples` section:

- Take doctest statements (`>>>` and `...` continuations), dropping lines marked
  `# doctest: +SKIP` and the expected-output lines.
- Keep the prefix up to and including the first statement that uses the symbol's name, at most
  12 statements.
- If no statement uses the symbol, the chunk has no example.

pydantic examples are the first code block in the section that names the symbol.

## Example check by execution (the user's M4 change)

- `scripts/run_examples.py` is stdlib-only and runs inside an environment as a worker. It reads
  examples as JSON lines on stdin and writes one result line per example as it finishes.
- Each example runs in a fresh namespace with `pd` and `np` preloaded (pandas environments) or
  `np` (NumPy environments). stdout and stderr are discarded, and the cwd is a temp directory.
- Results: `ok`, `error` (exception type and message), or `timeout`. Soft warnings are recorded
  with the harness's rules: deprecation and future warnings, plus migration-message patterns,
  attributed to the example's frames.
- Timeout is 10 s per example, enforced by the orchestrator. On a timeout the worker is killed,
  the example is marked `timeout`, and a new worker resumes at the next example.
- Every example runs in its tagged environment, then in the other environment of the same
  library. Kept when the tagged run is `ok`. `discriminative: true` when the other run is `error`.
  Dropped on `error` or `timeout` in the tagged run, logged with the reason.
- Results are cached in `data/corpus/{library}/example_checks.jsonl`, keyed by
  (environment lock sha256, example sha256), so a rebuild re-runs only changed examples.

## Retrieval (v0)

- Gold injection: each concept's `gold.old` and `gold.new` chunks are always present (controls:
  `gold.shared` in both versions).
- Distractors: `k_distract` (default 2) BM25 hits per version over the eligible chunks (D3),
  excluding gold symbols.
  - The query is the instance's query plus its context.
  - Tokenisation splits identifiers on dots, underscores and camel case, lowercased.
  - BM25 uses k1 1.5 and b 0.75, implemented in-repo (about 40 lines, no dependency); ties break
    on `chunk_id`.
  - The result depends only on the instance, so it is identical for every method.
- Order (L12): per concept, the targeted instances are sorted and a permutation seeded from
  `experiment.seed` and the concept id puts the target's gold chunk first in exactly half of
  them. An odd count puts the extra instance target-last and records it. Controls alternate by
  the same seeded rule. Each instance records `target_gold_first`.
- API: `retrieve(instance) -> RetrievedSet` (ordered chunks, each with role `gold` or
  `distractor`), `doc_conflict(chunks, diff)`, `keep_version(chunks, version)`, `dedupe(chunks)`,
  and `render(chunks, flags)`.
- Doc-conflict test: true when the set holds chunks from both versions and at least one chunk's
  symbols fall in `old_only`, `new_only` or `shared_changed` (D6). Otherwise the set is
  deduplicated to one chunk per symbol.

## Validation step 7

`varag.corpus.retrieve.check_gold_chunks(concept)` returns problems when any of these fails:

- A gold symbol has no chunk in its version's corpus.
- A keyword gold symbol's owner signature lacks the keyword (D5).
- A gold chunk's provenance is incomplete or its lock sha256 does not match the manifest.

Creating `corpus/retrieve.py` switches step 7 from skipped to enforced, so M4 lands only with
the four concepts passing it.

## Also in M4

`varag bench candidates --library <lib>` lists `old_only` and `new_only` pairings to mine for
concepts:

- Pairs come from `replacements.json` first, then from same-owner name similarity.
- Each pair is printed with whether both chunks have discriminative examples.

## Tests

Unit tests:

- Example extraction: SKIP lines, output lines, the prefix rule, the 12-statement cap.
- Five-part composition and order; the token cap and its trimming order.
- `strip_deprecation_notes` and `show_version_tags` rendering.
- BM25 determinism and tie-breaking; distractor eligibility (D3).
- Counterbalancing gives exactly half target-first per concept, identical across two calls.
- `doc_conflict` on fixtures; keyword gold resolved to its owner (D5).
- pydantic include resolution and section splitting.
- Provenance completeness.

Environment tests:

- The real corpus has gold chunks for every concept.
- The applymap and trapz gold examples are discriminative.
- The conflict test is true for the three concepts and false for the control.
- `bench validate` passes step 7 for all four.

## Out of scope

The v1 flags (`chunk_ratio`, `retrieval: end_to_end`, dense retriever), raw release-note
migration chunks (D4), and any use of the corpus by methods: that is M6.
